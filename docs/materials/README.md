# Materials for the realistic render

What every surface in the floor-plan models is made of, for the viewer's photorealistic mode: walls, floors, tiles, worktops, joinery, doors, windows, fixtures, switches. The machine-readable source is [`inputs/materials/catalogue.yaml`](../../inputs/materials/catalogue.yaml); this page is the readable view of it plus the reasons and the open questions. Scope is the ground floor (`ground_floor`) and the two bathroom models; the obývák acoustic roof model (`obyvak`) is out of scope (Petr, 2026-11-12: "I dont care about obyvak roof model, just the whole floorplan with furniture and fixtures").

The realistic mode does not reuse the solid-mode colours. Solid colours are diagram colours; these are the real or assumed finishes.

## How it fits together

- **Materials are keyed by id, never baked into geometry.** The models keep emitting meshes named `<label>__<id>__` (e.g. `cabinet__KR-ISL-END-N__`) or just `<label>`. Each catalogue entry's `applies_to.selectors` says which meshes it covers: `{label}`, `{label, ids}` or `{label, id_pattern}` (a regex searched in the id). The most specific selector wins (ids, then pattern, then label). Every label the three models emit has exactly one label-only selector, so no mesh is left without a material; `python -m blueprints.materials` checks that against the committed GLBs.
- **Real 3D fixtures later.** A glTF for a fixture (a tap, a light, a chair) names its material slots with catalogue ids (`chrome-polished`, `oak-natural-kaplan`, …). The viewer swaps each slot for the catalogue material with that id, so the fixture picks up the same finish and a later finish change is one catalogue edit. A slot with an unknown name keeps the glTF's own material. Nothing here assumes boxes.
- **Entries with `pending`** describe surfaces the models do not build yet (room floors, ceilings, door frames, window frames, blinds, facade). They are in the catalogue now so the finish decision is written down once.
- **Fields.** The contract is the comment at the top of `catalogue.yaml`. `base_color` is the albedo whenever there is no colour map (several sets ship only normal/roughness so plain painted surfaces stay even). `tile_size_m` is the real size of one texture repeat. `rotation_deg` is given where direction matters (oak grain, brushed steel): at 0 the grain runs along texture V.

## Textures

Texture sets live in `docs/materials/<id>/` because only `docs/` is published to Pages; a map path `docs/materials/x/color.jpg` is served at `<site>/materials/x/color.jpg`. They are JPEG (colour sRGB; normal in OpenGL convention, roughness and AO linear), 1024 px, 2048 px only for the oak and Silestone colour maps, and tracked with Git LFS like the GLBs. Each folder has a `LICENSE.txt` with its source and what was changed.

They are either CC0 scans (Poly Haven, ambientCG) re-tinted to the product's measured colour, or procedural textures generated in [`scripts/build_material_textures.py`](../../scripts/build_material_textures.py) with fixed seeds (own work, CC0). That script is the record of every tint and parameter and rebuilds all sets. Manufacturer photos were only measured (median colour of a centre crop, speck density by eye); none is shipped.
